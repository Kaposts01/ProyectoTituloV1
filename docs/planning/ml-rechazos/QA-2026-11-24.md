# Auditoria de viabilidad ML en la copia QA

Fecha local: 2026-11-24. **Resultado: P1 permite preparar reglas/anotacion limitada; P2 y el benchmark multicanal no son viables con los datos actuales de esta copia.** Esto no demuestra que los datos no existan en produccion u otros respaldos.

## Alcance y evidencia

Destino verificado: `127.0.0.1:5433`, base `crm_qa_local_20261118`, revision `20261118_0082`. Corte solicitado: `2026-11-24T00:00:00-03:00`; fecha efectiva de ejecucion UTC en el [JSON de agregados](qa-audit-2026-11-24.json). Se cuentan filas disponibles; el corte limita los calculos temporales, no transforma el inventario en una reconstruccion historica.

Herramienta: [audit_readiness.py](../../../scripts/ml/audit_readiness.py). Conexion directa a PostgreSQL, sin iniciar app/scheduler ni cargar `.env` automaticamente. Se verifica nombre de base, loopback, puerto, ausencia de opciones URL, `transaction_read_only=on` e aislamiento `repeatable read`. `search_path` controlado, timeout de sentencia 60 segundos, espera de bloqueo 3 segundos y rollback al terminar. Solo SELECT, sin migraciones, entrenamiento, backfill, ETL o proveedores.

El JSON conserva hash de la herramienta, revision, corte y agregados. No exporta ejemplos, glosas, codigos individuales, IDs, nombres ni atributos personales. Para medir normalizacion y señales de texto personal se procesan solo codigo/glosa agrupados en memoria, sin persistirlos. El detector de email/RUT es parcial: cero coincidencias no certifica anonimato ni ausencia de PAN, telefono u otros datos.

## Viabilidad por capacidad

| Capacidad | Estado local | Siguiente condicion |
|---|---|---|
| Taxonomia y reglas | Se pueden diseñar/probar con ejemplos sinteticos y catalogos existentes | Revisar familias, submotivos, desconocidos y restricciones con negocio antes de codificar mapeos definitivos. |
| P1 TCH | Posible iniciar anotacion saneada; entrenamiento no justificado | Revision humana de combinaciones, clases y cobertura; evaluar primero reglas. |
| P1 VP/Toku/Payku con historico real | No evaluable en esta QA | Obtener copia representativa o reportes por procedimiento separado autorizado. No llamar proveedores por disponer de una key. |
| P2 cualquier canal | No viable para entrenamiento o evaluacion | Core trazable, episodio/obligacion vinculados y ventana de resultado observable a 30 dias; datos y etiquetas por revisar. |
| Comparacion de modelos y KPI de impacto | Prematuros | Primero resolver datos; despues protocolo y benchmark. Impacto requiere seguimiento prospectivo y control de sesgo de gestion. |

La inspeccion de codigo confirma que `write_virtualpos.py` crea `charge_recoveries` con cierre a cuatro dias y su conciliacion observa estado. Aun con filas, no seria automaticamente una etiqueta a 30 dias ni la fecha real del pago. TCH conserva una ultima fila por cuota; Core puede usar inicio del periodo como fecha de vencimiento de respaldo, que tampoco debe convertirse en fecha real de rechazo.

## Reproduccion y pruebas

Desde la raiz y con una URL QA suministrada privadamente en `ML_AUDIT_DATABASE_URL` (no pegarla en argumentos, Git o informes):

```powershell
.venv/Scripts/python.exe -m scripts.ml.audit_readiness --expected-database crm_qa_local_20261118 --as-of 2026-11-24T00:00:00-03:00 --out .local/ml-readiness-repeat.json
.venv/Scripts/python.exe -m pytest scripts/ml/tests/test_audit_readiness.py --noconftest --basetemp=.local/pytest-ml-audit-repeat -q
.venv/Scripts/ruff.exe check app tests alembic scripts
```

13 pruebas puras pasan: destinos no QA/puerto/host/opciones inseguros, configuracion y verificacion efectiva de transaccion, corte temporal, agregacion sin ejemplos y errores sin secretos. `--noconftest` evita inicializadores de app/base; el directorio temporal dentro de `.local/` evita un permiso denegado del Temp de Windows detectado en la primera corrida. No se ejecuta la suite DB que crea/migra bases, porque no cambia la aplicacion.

Ruff completo pasa. No corresponde build frontend ni entrenamientos: no se modificaron interfaz, runtime de la app, dependencias o modelos. Se revisan diff y exclusiones de skills antes del commit local.

## Limites y acciones propuestas

Esta es una fotografia QA del respaldo antiguo restaurado, no una auditoria actual de produccion. Tener el esquema 0082 no implica tener sus datos historicos. Las cuentas y el estado de QA no deben extrapolarse a toda la fundacion.

La siguiente entrega util es revisar la taxonomia y preparar anotacion TCH, o acordar una copia de datos representativa. Materializar Core, importar reportes o recuperar otro respaldo requiere una tarea separada con plan de respaldo/reconciliacion. No se hizo ninguna de esas operaciones aqui. Las reglas actuales, el Dashboard y sus definiciones financieras permanecen intactos.
